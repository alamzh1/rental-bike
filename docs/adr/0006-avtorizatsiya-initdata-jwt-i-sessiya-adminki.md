# 0006. Авторизация: initData → JWT для Mini App, отдельная сессия для админки

## Контекст
Регистрации с паролем нет, роль (клиент, менеджер, администратор) определяется по Telegram ID. Нужно, чтобы клиент не видел чужие брони и документы.

## Решение
Mini App отправляет initData, API проверяет подпись (HMAC-SHA256, `auth_date` ≤ 24 ч) один раз и выдаёт JWT на 24 ч; дальше `Authorization: Bearer`. Заголовок `tma <initData>` принимается тоже. Админка входит через Telegram Login Widget и получает httpOnly-cookie сессию (12 ч); изменяющие запросы обязаны нести `x-admin-request`. В dev включается `DEV_AUTH=1` с тестовыми пользователями, в проде выключено.

## Почему
- Проверка подписи initData на каждом запросе отвергнута: дорого и избыточно, JWT закрывает ту же задачу после одной проверки.
- Общий токен для Mini App и админки отвергнут: у админки другой вход (Login Widget вне Telegram), другой срок жизни и защита от CSRF через cookie.
- Пароли и регистрация отвергнуты брифом.

## Последствия
- Отозвать доступ (например, снять роль менеджера) до истечения JWT на 24 ч нельзя без проверки роли на сервере при каждом запросе; роль надо читать из БД, а не из токена.
- `DEV_AUTH` — опасный флаг: если он окажется включён в проде, любой войдёт любым пользователем.
- В dev оболочка Mini App и API расходились по формату dev-входа (неподписанный initData с `hash=dev` против `{devUser}`), это известный долг.
- Права менеджера в админке ограничены списком сегментов API на сервере, а не только скрытыми разделами интерфейса.
